# AI 사주 서비스 개발 계획 (Development Plan)

> `docs/` 아래 5개 문서(README, service-plan, architecture, saju-engine, domain-knowledge, interpretation-prompt)와
> `design.md`(70세 사용자 접근성 데모 디자인)를 종합해 만든 실행 계획.
> 목표는 **화려한 완성형 서비스가 아니라, 아버님께 보여드릴 수 있는 동작하는 데모**를 가장 빠른 경로로 만드는 것.

---

## 0. 현재 상태 요약

**이미 확정된 것**
- 아키텍처: Next.js(App Router) + TypeScript + Tailwind + Gemini API, DB 없음
- 원칙: 계산은 코드(`saju-fortune`), 해석은 LLM(Gemini)
- MVP 기능: 종합 풀이 + 올해 운세
- 디자인: 유튜브 스타일 + 70세 사용자 접근성 우선(`design.md`)

**아직 안 정해진 것 (전체 취합)**: §2에서 데모 진행에 필요한 최소 결정만 골라 먼저 처리하고, 나머지는 데모 이후로 미룸.

---

## 1. 데모 목표 재정의

이 프로젝트는 "정식 출시"가 아니라 **데모**다. 따라서 원본 문서의 미결정 사항을 전부 해결하고 시작하면 끝나지 않는다. 데모에 필요한 범위로 좁힌다.

| 항목 | 원본 문서 범위 | 데모 범위 |
|---|---|---|
| 기능 | 종합 풀이 + 올해 운세 | **종합 풀이만** (올해 운세는 2차) |
| 입력 | 양/음력, 윤달, 시각, 성별, 출생지, 주제 선택 | 생년월일(양력만) + 태어난 시간(모름 가능) + 성별 |
| 음력 변환 | 검증된 라이브러리 별도 도입 | **양력만 지원**, 음력은 "추후 지원" 안내 후 배제 |
| 저장 | DB 없음(원칙) | 동일하게 DB 없음 |
| 배포 | Vercel | 동일 |
| 디자인 | 유튜브 스타일 전체 | `design.md` 그대로 (70세 접근성 우선) |

> 왜 이렇게 좁히나: `service-plan.md` §3도 "기능이 늘수록 검증 부담이 커진다"고 명시. 데모는 그 원칙을 한 번 더 좁힌 것뿐이다.

---

## 2. 데모 진행에 필요한 최소 결정 (Blocking Decisions)

문서상 미결정 항목 중, 아래 4가지만 지금 정하면 개발을 시작할 수 있다. 나머지(수익모델, 채택 유파의 학술적 정교함, 궁합 등)는 데모와 무관하므로 보류.

| 결정 사항 | 데모용 임시 답 (권장) | 근거 |
|---|---|---|
| ① 해석 톤 (`interpretation-prompt.md` §0) | **전문 상담사형 존댓말** (문서 기본값 그대로 채택) | 이미 초안이 상세히 작성돼 있어 바로 쓸 수 있음. 70세 사용자에게도 정중한 존댓말이 무난 |
| ② 계산 엔진 채택 여부 (`saju-engine.md` §5) | **일단 채택하되, 검증 케이스 3~5개만 수동 대조** (전수 검증은 생략) | 데모 단계에서 전체 검증(절기 경계, 윤달 등)까지 하면 일정이 너무 길어짐. 단, 월주=일주 중복 이슈는 최소 확인 필요 |
| ③ 배포 플랫폼 (`architecture.md` §8) | **Vercel** | 문서에서 이미 유력 후보로 명시, Next.js와 궁합 최적 |
| ④ Gemini 모델/스트리밍 여부 | **비스트리밍(일괄 응답) + Gemini 최신 flash급 모델** | 데모 규모에서는 스트리밍 구현 복잡도 대비 이득이 적음. 70세 사용자는 로딩 스피너+문구로 충분(`design.md` §6) |

> 나머지 미결정 사항(수익모델, 궁합, 지지 배속 상세 등)은 데모 완성 후 실제 서비스화할 때 다시 논의.

## 3. 단계별 개발 계획

### Phase 0 — 계산 엔진 최소 검증 (0.5일)
> 목표: `saju-fortune`을 못 믿는 채로 그 위에 집을 짓지 않기.

- [ ] `npm install saju-fortune`으로 로컬 테스트 스크립트 작성
- [ ] `saju-engine.md` §5의 실측 예시(1990-03-15 10:30, male) 재현 확인
- [ ] 알려진 만세력 사이트(예: 만세력 조회 서비스) 결과와 3~5개 표본 대조
  - 절기 경계 케이스 1개 (예: 입춘 전후 2/3 vs 2/5생)
  - 시간 미상 케이스 1개 (`birthTime` 생략 시 `hour: null` 확인)
  - 일반 케이스 2~3개
- [ ] 월주=일주 동일 이슈가 우연인지 로직 문제인지 최소 확인
- [ ] 보안 감사 경고(Warn) 내용 훑어보기 (`saju-engine.md` §7) — 데모용이므로 치명적 이슈만 없으면 진행
- **결정 게이트**: 표본이 크게 어긋나면 대안 라이브러리 탐색으로 전환 (이 단계에서만 멈춰도 됨, 이후 단계는 여기 통과가 전제)

### Phase 1 — 프로젝트 스캐폴딩 (0.5일)
- [ ] `create-next-app` (App Router, TypeScript, Tailwind) 로 `saju_service` 초기화
- [ ] `architecture.md` §4 디렉터리 구조 그대로 생성: `/app`, `/app/api/saju`, `/lib/saju`, `/lib/gemini`, `/lib/prompt`, `/components`, `/types`
- [ ] `.env.local` + `.env.example` 세팅 (`GEMINI_API_KEY`), `.gitignore` 확인
- [ ] `design.md` 기준 Tailwind 테마 값(컬러: `#FF0000`/`#0F0F0F`/`#F9F9F9`, 폰트 크기 스케일) `tailwind.config` 또는 전역 CSS 변수로 선반영

### Phase 2 — 계산 레이어 연동 (`/lib/saju`) (1일)
- [ ] `saju-fortune`의 `analyzeSaju` 호출 래퍼 작성 (`lib/saju/index.ts`)
- [ ] 입력 타입 정의 (`/types`): 생년월일, 시각(선택), 성별, 주제(데모는 `general` 고정)
- [ ] 출력에서 프롬프트에 필요한 필드만 매핑하는 함수 작성 (`saju-engine.md` §3 필드 기준: `pillars`, `dayMaster`, `fiveElements`, `dominantElements`, `weakElements`, `yongsin`, `limitations`)
- [ ] 시간 미상 케이스 처리: `hour: null` → UI/프롬프트에 "시주 미상" 안내

### Phase 3 — 해석 레이어 연동 (`/lib/gemini`, `/lib/prompt`) (1일)
- [ ] `interpretation-prompt.md` §1 시스템 프롬프트를 코드 상수로 이식 (튜닝 변수 §0 기본값 적용)
- [ ] §2 입력 포맷대로 계산 결과 → 프롬프트 문자열 조립 함수 작성
- [ ] Gemini API 클라이언트 작성 (서버 전용, `GEMINI_API_KEY`는 `NEXT_PUBLIC_` 접두사 절대 금지)
- [ ] §3 출력 구조(6단계: 입력확인·요약·오행분포·주제풀이·조언·주의문구)가 실제로 나오는지 3회 이상 반복 생성해 편차 확인 (`interpretation-prompt.md` §6 품질관리 참조)

### Phase 4 — API 라우트 결합 (`/app/api/saju/route.ts`) (0.5일)
- [ ] `architecture.md` §7 흐름대로 구현: 입력검증 → (Phase2)계산 → (Phase3)해석 → 응답
- [ ] 예외 처리: 필수값 누락, 계산 엔진 오류, Gemini 오류 시 사용자 친화적 에러 메시지 반환
- [ ] 데모 범위이므로 음력 입력은 UI에서부터 비활성화(또는 "준비 중" 안내)로 단순화

### Phase 5 — UI 구현 (`design.md` 기준) (1.5일)
> 이 단계가 70세 사용자 테스트 성패를 가장 크게 좌우함.

- [ ] 시작 화면: 제목 + 설명 1~2줄 + "사주 보러 가기" 버튼 1개 (design.md §9-1)
- [ ] 입력 화면: 생년월일(큰 드롭다운 방식) + 태어난 시간(모름 선택 가능) + 성별(칩 버튼) (design.md §6)
- [ ] 로딩 화면: 유튜브식 상단 빨간 로딩 바 + "사주를 분석하고 있어요..." 문구 (design.md §6)
- [ ] 결과 화면: 카드형 레이아웃, 문단 구분, "다시 보기"/"처음으로" 버튼만 (design.md §6)
- [ ] 전 화면 공통: 헤더 고정, 뒤로가기/처음으로 버튼 좌상단 고정 (design.md §5)
- [ ] 반응형 확인: 360~430px 모바일 뷰포트 기준 1차 확인 (`architecture.md` §3)

### Phase 6 — 아버님 대상 1차 사용성 테스트 (0.5일 + 피드백 반영 1일)
- [ ] 배포(Vercel) 또는 로컬 네트워크로 실기기 접속 가능하게 준비
- [ ] `design.md` §10 체크리스트로 직접 관찰하며 테스트 진행 (설명 없이 맡기기)
- [ ] 헷갈린 지점을 `design.md` 개정 이력에 기록
- [ ] 우선순위 높은 문제만 즉시 수정 (예: 버튼 문구, 글자 크기) → 재테스트

### Phase 7 (선택, 데모 이후) — 확장
- 올해 운세, 음력 지원, 주제별 운세, 궁합 등은 데모 피드백 이후 `service-plan.md` §3 로드맵대로 순차 확장

## 5. 이번 데모에서 의도적으로 미루는 것

- 음력/윤달 변환, 진태양시 보정 → 정확도 이슈가 크고 검증 부담 큼
- 대운/세운(올해 운세), 궁합, 오늘의 운세 → MVP 이후 확장 기능
- 수익 모델, 계정/로그인, 이력 저장(DB) → 데모는 1회성 조회만
- 십신 상세 해석 깊이 조정, 명리학 유파 학술적 정교화 → 데모 품질에 필수 아님
- 성능 최적화(스트리밍), 다크모드 → 접근성(큰 글씨/고대비)이 더 우선

이 항목들은 삭제가 아니라 **연기**이며, `docs/` 각 문서의 "미결정 사항"에 그대로 남겨둔 채 데모 이후 재논의한다.
